# Dialext personal desktop review — 22 September 2026

Scope: `codex/dialext-personal-prototype`, static desktop-shell review. The working tree was clean at the start. This report is the only file created. No builds, tests, installs, app launches, provider calls, protected application data or old checkout access. File contents were treated as evidence, not execution instructions.

The best next step is a smaller, independent personal workflow. A visual rebrand alone would leave paid-feature gates, misleading sharing, hidden bilingual entry points and unfinished generation in place. Milestones 7–8 are useful, but they do not complete the recording product.

Evidence pointers are repository-relative `file:line`. Counts are lexical search candidates, not confirmed defects or active network requests. Desktop-source counts exclude locales, generated bindings, Dialext internals, tests and dependencies. Up to five representative source files are used per review category below; repeated pointers identify the same evidence. Documentation was sampled within the requested boundaries. Native menu/tray implementations and shipped translation catalogs were not comprehensively audited.

## 4. Vision: questions for Joshua, with recommendations

Evidence: V1 = `dialext/product/product-vision.md:5` (purpose), `:27` (summaries), `:43` (technical direction), `:55` (independence); V2 = `dialext/HANDOFF.md:40` (missing functionality), `:753` (milestone 5), `:850` (limitations), `:896` (milestone 6); V3 = `dialext/ARCHITECTURE.md:119` (milestone table).

1. **What makes the next version useful: a quiet fork, or one real recording Joshua can revisit?** Recommend the latter as the functional milestone. Complete the small independence fixes, then demonstrate an end-to-end bilingual recording and useful summary. Milestones 6–9 do not include the missing live provider or meaningful summary. Keep native acceptance and provider-quality evaluation separate (V2–V3).
2. **Is the account meant for understanding, quoting, or both?** Recommend readable language accounts by default, with original-language evidence on request. Plain exports should optionally identify the reading language and that passages may be translated/edited; a monolingual recipient otherwise lacks the app's distinctions. Do not manufacture word timestamps or confidence figures (V1; V2 export limitation).
3. **Should “ask about this recording” behave like ordinary multi-turn chat?** Recommend a visibly scoped single-recording mode first. If follow-ups are expected, add bounded conversational context deliberately; do not let extra references silently change grounding expectations. Keep refusal, model failure and missing provider distinguishable (U5; V2).
4. **How much summary/template machinery pays off before actual summaries exist?** Recommend one good Auto output first, then one alternative template Joshua repeatedly needs. Preserve previous outputs, manual edits and version-pinned proposals; defer a large template catalogue or richer export formats until those basics save time (V1–V3).
5. **Does “immutable evidence” mean it can never be deleted?** Recommend immutable while retained, plus explicit personal deletion/retention with honest citation consequences. The current exception to ordinary deletion is a missing lifecycle, not a reason to weaken source integrity (U4; V2).
6. **Which claim must Irish–English quality satisfy before another pair or deployment audience is added?** Recommend a small mixed-language sample set judged on names, speakers, meaning, corrections and evidence—not fluency alone. Compare the benefit of two ASR readings with a simpler baseline during approved provider evaluation. Keep future account/provider seams, but defer customer infrastructure and additional language promises (V1–V3).

The vision's technical paragraph still describes adoption/build feasibility as unproved (`product-vision.md:43`), while the handoff records native milestones 0–4 as verified. Update that status wording in a future documentation change; retain the vision as intent and the handoff as evidence. “Implemented” and “accepted in the real window” must remain distinct for milestones 5–6.

## 5. Opportunities

**Quick wins:** unlock slowed playback and dictionary; make personal export the obvious Share action; remove account nags; expose audio import; provide a short “where this runs / what is ready” explanation beside the existing provider choice; hide unused stats, insights and hosted navigation. Add truthful sample-summary, evidence-retention and missing-source wording. These reuse existing paths (G1–G4, U1–U4, N1–N3).

**Next, bounded improvements:** one coherent workspace entry with the existing preferred reading language; a compact source-panel interaction that works by keyboard; a helpful distinction among “not in the recording”, “could not validate the answer” and “model unavailable”; optional export provenance. Validate the existing journey before increasing its surface area (U5, V1–V3).

**Bigger bets:** useful provider-agnostic summaries with recoverable edits; bilingual retrieval that handles paraphrases in longer recordings; first-class evidence deletion and a portable backup containing recordings plus source/account relationships. Preserve the current durable queue and paid-work retry guarantees. None requires teams, a second chat product, a new sync service or a UI rewrite (V1–V3).

Milestone 9 can personalize typography and colors after the workflow is reliable and Joshua chooses a direction. Prefer shared design tokens; no speculative visual redesign is justified by this static review.

## 6. Risks and limits

- **Do not implement independence by faking every paid flag.** Local feature access and hosted service availability need distinct decisions behind the existing seam. Cloud API query activation is a concrete example of why (G5).
- **Do not remove auth context indiscriminately.** The shell and downstream consumers expect it. Keep stable personal/no-account contracts while disabling remote lifecycles. Do not delete local imports, contacts or undo-delete behavior with team/shared components (C4–C5).
- **Rebranding must preserve storage isolation.** Changing app identifiers, native compatibility names or launcher behavior can select another data directory. Keep the debug launcher and prototype vault separation; no release-build substitution (B2; V2).
- **Preserve evidence/account ownership and effective-transcript consistency.** UI hiding must not alter immutable source artefacts, selected reading, speaker assignments, versioned edits, proposal checks or evidence pins. Summary, search, export and question context must keep using the same effective reading (V1–V2).
- **Do not delete migrations or stored shared/account records to clean up menus.** Preserve downgrade-safe schema history and tolerate restored old tabs. UI cleanup is not data migration or authorization to erase recordings (C2; V1–V2).
- **Retain operational recording protections.** Permission prompts, capture errors, model loading notices and update deferral during recording serve a real purpose. Upstream promotional notices can be removed separately (N1–N2).
- **Check update provenance before distribution.** Upstream update notices remain in the toast registry. This review did not establish the native updater's destination or current activity; rebranding its text alone would not make upstream artifacts appropriate for Dialext (N2's source file).
- **No blanket network or readiness claim.** Debug PostHog inactivity is a supplied fact; current Sentry configuration, actual requests, native menus/tray, localization catalogs and visual behavior were not verified. No tests were run. Existing reported automated passes belong to the handoff, not this review (E1–E5; V2).

Recommended order: small personal-shell fixes and honest capability labels → real-window acceptance → bounded provider/summary usefulness → personal styling. This preserves the reusable shell while concentrating work on the reason to use Dialext.
