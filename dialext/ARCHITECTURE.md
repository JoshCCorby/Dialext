# Personal Dialext: implementation decisions

Updated 17 September 2026. This is the implementation direction for the next sessions, not a description of completed features. The user's [product brief](product/product-vision.md) is authoritative. Build one milestone at a time; prove it in the desktop interface before adding the next.

## Product and reuse boundary

Adapt Anarlog's community desktop application. Keep its working editor, contacts, templates, local database, search and export machinery. Do not rebuild its interface in the old web application or start another application beside it. Office deployment, organisation administration, billing, enterprise capture and Teams integration are outside the current scope. Do not remove every upstream feature in a sweeping cleanup: hide distractions only as a separately tested navigation change.

The product is a personal recording library with an understandable account in the reader's preferred language. Start with Irish–English. Generate the preferred language first; another language is an explicit request, not a second mandatory pane. The audio remains in its original language. Translation status and uncertainty are separate facts. Unknown original language remains unknown; a forced ASR locale does not establish what language was spoken.

One application owns all saved user work. The old `Transcip` checkout is a source reference with existing, uncommitted work and real data; do not reset it or connect its database as a second live authority. No old credentials or recordings have been migrated.

## Data ownership

Use Anarlog's SQLite database for workspace state. Add schema through `crates/db-app` migrations, with native transactions exposed by `plugins/db`. Do not create schema in TypeScript or a separate Node database.

| Data | Owner and treatment |
| --- | --- |
| Original audio | App-managed attachment in the local vault, with content digest and measured duration. Never replaced by a translation. |
| Independent ASR readings | Immutable, versioned evidence artefacts. Preserve the provider's words, real timing and original speaker labels. Store a digest and locator in an app-owned evidence table. |
| Readable language account | One canonical editable `transcripts` row per account version. An account registry associates it with recording, target language, generation version and evidence digest. The account is derived prose, not verbatim evidence. |
| Current reading | An explicit active account ID for each Dialext recording. Changing selection must not replace another account's text or edits. |
| Corrections | A native transaction updates the canonical account and appends a recovery/history entry. History is not a second editable copy. Record account ID, previous revision/hash and changed passage IDs. |
| Speaker identity | A stable recording-level speaker ID, distinct from every provider's raw speaker label and from a reusable contact ID. |
| Summaries and notes | Existing session documents. New template outputs preserve earlier outputs. Personal notes are not silently treated as recorded speech. |
| Model proposals | Explicit pending versions pinned to the exact account and document versions used to prepare them. Only acceptance changes the document. |

The first import currently retains original evidence and the supplied alternate account inside session metadata. That is a bounded fixture/import seam, **not the final evidence store**. Replace it with owned artefacts and a registry before supporting normal recording sizes. The native ingest limit is 2 MB, including both the original bundle and the selected working account. Do not simply raise the limit or duplicate whole evidence bundles across language accounts.

Do not use soft deletion to hide unselected accounts. Deletion has separate retention and restoration semantics.

### Milestone 1 schema contract

Use these names so the next slice does not need another architecture exercise. Add an additive migration after the repository's actual latest migration; do not reuse old Dialext migration numbers.

- `dialext_recordings`: `id` (the existing session ID), `active_account_id`, `preferred_language`, and creation/update timestamps. Canonical language codes are `en` and `ga`; the prototype bundle's `english`/`irish` strings are mapped at its boundary.
- `dialext_evidence`: `id`, `session_id`, `kind` (`audio` or `asr`), `source_id`, `revision`, `sha256`, app-owned relative `artifact_path`, optional measured `duration_ms`, and timestamps. Require a unique `(session_id, source_id, revision)`. Paths are generated by the application, not accepted as arbitrary filesystem locations from a bundle.
- `dialext_accounts`: `id`, `session_id`, `transcript_id`, `target_language`, `generation`, `input_evidence_digest`, `original_artifact_path`, `original_sha256`, and timestamps. Require unique `transcript_id` and `(session_id, target_language, generation)`. Link only to a transcript in the same recording. Retain the existing transcript `content_revision` and trigger-maintained `content_version`; do not invent another independently mutable text revision in this table. The original account artefact is derived output, never an ASR evidence leg.

The account registry contains **no competing editable text**. Generated originals live as immutable app-owned artefacts; the `transcripts` row owns the current editable account. A changed generation creates a new account/transcript, preserving the edited predecessor. The active-account update and search-dirty notification are one transaction. A recording with no selected usable account is explicitly “preparing/unavailable”, not a fallback that concatenates every language.

Enforce same-recording ownership for both `active_account_id` and `transcript_id` inside native transactions, with database constraints/triggers where practical. Reject an absent, deleted or foreign account. Selection accepts the expected previous account ID so two windows cannot silently overwrite one another's selection. Keep the UI on the previous view until the transaction succeeds. Selection changes future transcript context; it never translates or regenerates an existing summary.

The filesystem and SQLite cannot share a transaction. Validate and hash a bounded artefact, write to a temporary file in the vault, then atomically publish complete bytes to an application-generated immutable path (the prototype uses a no-clobber hard link and removes the temporary name) before committing its database reference. A crash may leave an unreferenced file, but must not leave a committed row pointing to a partial file. Never overwrite an existing path with different bytes. Check existence and digest when loading evidence; missing or corrupt evidence disables source-dependent work without deleting the editable account. Defer garbage collection until references, rollback and restoration are handled deliberately.

Define hashes over a documented versioned byte representation. Hash source files over their original bytes; form an account's evidence-set digest from a deterministically sorted list of source IDs, revisions and source digests. Do not rely on JavaScript object insertion order. Preserve exact anchor-to-evidence-version associations, including when two provider runs reuse the same source ID.

Add speaker mappings and edit history only in their later milestones. Use one TEXT primary key and defaults/nullability as required by the database instructions, but keep these personal-only tables out of enabled cloud-sync policy. Do not add organisation or tenant columns merely because the old application had them. Soft-deleting a recording hides its accounts and search content while retaining its artefacts for restore; do not cascade physical file removal from an ordinary delete.

For the prototype metadata migration, preserve the already edited selected transcript in place. Build the alternate account from the retained original bundle, write artefacts, then commit the registry and a migration marker together. Retry idempotently after interruption. Keep the original metadata bundle until the migration has been verified; never reimport its selected text over saved edits.

## One effective transcript across the application

Adding an Irish transcript beside an English transcript currently makes upstream readers concatenate both. A language dropdown that filters only the visible component would recreate the old frontend/backend mismatch.

Introduce a shared database view or equivalent central native projection that returns:

- all normal upstream transcripts for an ordinary Anarlog recording;
- exactly the selected account's transcript for a Dialext recording.

Keep explicit account-by-ID reads for editing and source review. Route every *effective recording* read through the selected-account projection. Audit at least these existing seams:

| Consumer | Current seam |
| --- | --- |
| Transcript panel, renderer and editing | `apps/desktop/src/stt/queries.ts`, `session/components/note-input/transcript/state.ts` |
| Copy and export | `session/components/note-input/transcript/render-request-hooks.ts`, `export-data.ts` |
| Summary generation and chat context | `session/content-queries.ts:loadSessionContentSnapshot`; consumers in `services/enhancer/` and `chat/tools/` |
| Native CLI/MCP/export access | `crates/db-app/src/session_ops.rs:list_session_transcripts`, `crates/agent-access/src/lib.rs` |
| Search | Trace the transcript index triggers and their consumers from `crates/db-app/migrations/20260714120300_search_index_transcripts_triggers.sql`; do not assume changing the visible list changes the index. |

Switching accounts must atomically change the selection, invalidate/rebuild the affected search document and notify readers. Test that search, export and question context show the chosen corrected text after restart. The registry also needs deletion/restoration handling; a new table is not complete until those paths are covered.

## Evidence, timing and speaker mapping

Each passage needs a stable ID, its text, recording-level speaker ID, target language, original-language annotation and exact source anchors `(source_id, start_ms, end_ms)`. Anchors resolve to a specific immutable evidence version. Never recover one by fuzzy time matching or transcript text similarity.

The imported validator proves structural properties, not linguistic correctness. Its inherited `language` output is the **target** language; it does not preserve a segment's spoken language. Keep a separate `spoken_language` field. The bridge explicitly defaults that field to `unknown` and checks the passage interval against its supporting anchors.

Upstream timing defaults missing metadata to `provider_word`. Derived wording must not fall through to that default. The import marks it `synthetic_text`, which disables unsupported word seeking. When implementing listen-back, add an explicit anchored-passage action that plays the source interval. Do not manufacture per-word timestamps by dividing translated sentences evenly across an interval.

Provider speaker labels are scoped to their independent ASR sources. `irish-asr/Speaker 1` and `english-asr/Speaker 1` are not automatically one person. Introduce explicit source-speaker mappings when producing an account; ambiguous attribution stays unknown. User naming associates the recording-level speaker with an existing or new Anarlog contact, updating all account views for that recording. Reuse the existing contact search and whole-session speaker picker. Do not add voice recognition to remember Gary.

## Corrections and summary proposals

Do not reuse a generic transcript update that silently retries against a changed base for version-sensitive Dialext edits. Submit account ID, expected `content_version`, passage IDs and proposed text. The existing `20260907120100_transcripts_content_version.sql` trigger changes this token even when a writer changes `words_json` without bumping `content_revision`; a revision counter alone is therefore insufficient. Check and write in one native transaction; on mismatch retain the person's typing and ask them to refresh/review. Append-only undo is another checked edit. Preserve the immutable evidence and original account generation.

Read the existing `session/queries/proposals.ts` before extending it. It currently checks `base_updated_at`, then performs the document update and proposal-status update separately. That is useful interface infrastructure, **not an atomic stale-write guarantee**. Correction-driven proposals need:

1. Account ID plus transcript `content_version`, document ID plus document `content_version`, and stable target block IDs. Documents already have a corresponding trigger-maintained version; reuse it rather than timestamps.
2. A proposed change to affected blocks only; no unsolicited replacement of unrelated manual edits.
3. Atomic comparison of both input versions, application of accepted changes and transition of proposal status.
4. A visible stale outcome on mismatch, leaving the document untouched.

A new template is a separate output/version. Auto should adapt headings to the recording; do not transplant the old mandatory decisions/actions minutes schema.

Store summary evidence alongside stable blocks when generating them. An edited block must not keep an apparently verified source association unless its text still matches the pinned content. Do not infer provenance later from bullet position, and do not let Markdown round-trips silently discard block identity. Expose one source/detail control on hover, focus or selection; transcript marks and chat citations reuse the same source-audio panel.

## Processing boundary

Use a native-owned durable task queue in the app database. A development Node helper can reuse the original JavaScript engine as a **stateless subprocess**, invoked with an argument array and bounded JSON input/output. It has no HTTP listener, database connection or authority to edit the workspace. Rust owns task state, cancellation, result validation and durable writes. Keep diagnostic logs on stderr, protocol events on stdout, and reject unknown protocol versions or oversized results.

Start by extracting pure request builders, normalisers and validators with their tests. Do not copy the old worker, organisation repository layer, request handlers or the entire deployment stack. Relevant original source seams include:

- `pipeline/asr/azure.mjs:normalizeAzureResult` and its independent-language call path;
- `pipeline/transcript/reconstruct.mjs:buildReconstructionRequest` and `reconstructTranscript`;
- `pipeline/transcript/reconstruction-validate.mjs` (already copied, unchanged);
- `pipeline/chat/answer.mjs:buildChatRequest` and `pipeline/chat/citations.mjs:validateChatAnswer`.

The provider functions have legacy configuration/gate dependencies; they are not ready-made portable modules. Preserve validation while removing deployment coupling deliberately. Secrets stay in the native/helper environment, never in renderer state, JSON fixtures or Git. The provider interface is extensible, but only tested language/provider pairs are offered as supported.

Persist each successful paid stage separately. Retrying a failed reconstruction must not rerun successful ASR. Request keys include audio digest, source locale, provider/model, relevant prompt version and target language. A crashed or cancelled task cannot keep displaying healthy progress; late results must be fenced by task attempt and input revision. Do not invent elapsed-time percentages.

Use deterministic fixture providers for interface and crash/retry testing first. The expired Azure credential is not a blocker to those tests. Packaged runtime distribution and a first short live-provider run are later milestones, not reasons to restore enterprise deployment work.

## Ordered implementation milestones

| Milestone | Bounded work | Acceptance before proceeding |
| --- | --- | --- |
| 0 — native baseline | Finish the isolated native launch; use the prepared sample through Settings → Imports. | Open summary/transcript, edit text, assign a speaker, export, close/reopen. Record exactly which steps were verified. No mocked DB substituted for this check. |
| 1 — durable accounts | Add evidence/registry migrations and selected-account projection, with default English and saved preference. Migrate the sample metadata format idempotently. No provider calls. | Both prepared accounts can be selected; independent edits survive switching/restart; UI, search, export, enhancer and chat inputs agree; ordinary Anarlog sessions still work. |
| 2 — source review and speaker identity | Attach synthetic source audio with real measured intervals; add one anchored playback panel, translation/unknown-language labels and persisted recording-to-contact assignments. | Exact audio interval, keyboard-accessible reveal, two-provider labels never conflated, Gary remembered on another recording, selected-language exports use his name. |
| 3 — checked editing and proposals | Native version-pinned account edits/history and atomic summary proposals; use deterministic summary outputs and existing template UI. | Stale edit/proposal refuses without lost typing; undo survives restart; accepting a targeted proposal preserves unrelated manual edits; applying Lecture creates another output. |
| 4 — provider bridge | Native task lifecycle plus stateless helper and independent-stage persistence. Wire preferred-language generation, then on-demand alternate generation. | Cancel/restart/failure tests preserve successful stages; no duplicate paid ASR on downstream retry; one approved short live sample assessed separately. |
| 5 — coherent personal workflow | Quiet source controls on stable summary blocks, footer question input, corrected-text retrieval and simple TXT/Markdown sharing. | A question months later uses the chosen effective account, refuses missing evidence, and opens the same source panel; exports match what the reader sees. |

Milestones are implementation scopes, not instructions to defer all interface work until the end. Every milestone includes a visible, testable desktop path. Stop a slice from expanding into rebranding, new cloud infrastructure, all-language support or a second chat product.

## Final acceptance matrix

Keep a two-speaker mixed Irish/English fixture and a second recording reusing a contact. Exercise English and Irish selection, an unknown-language passage, missing alternate account, wrong/near-match anchors, a corrected phrase, stale writes, refusal/cancellation, duplicate import, restart, search, text export and unavailable provider credentials. Check original evidence digests before and after edits. Add a representative real evaluation set before making accuracy claims; fluent generated text is not evidence of correctness.
